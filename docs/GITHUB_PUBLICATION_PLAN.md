## 3. Отдельно выбрать лицензию

Владелец разрешает обсуждать открытое использование своих наработок,
но конкретную лицензию ещё не выбрал. Следующим отдельным шагом объяснить
варианты, определить границы для кода и фирменных материалов, затем добавить
полный `LICENSE` и необходимые уведомления о сторонних материалах.
Сейчас лицензия самовольно не назначается.

## 4. Зафиксировать точный состав публикации

- `output/` с посторонними документами уже исключена из Git и Docker.
- Настоящие `.env`, локальные архивы, резервные копии, зависимости, кэши,
  сборки и готовые видеоролики не включать. Исходники ролика в `design/reels/`
  можно сохранить: это отдельный проект с описанием материалов и их прав.
- Действующие исходники, миграции, lockfiles, тесты и фирменные изображения
  оставить. Исторический код в `archive/reference/` — справочный материал,
  а не зависимость действующей игры. Удалять всё содержимое папки проекта
  для уменьшения размера не нужно.
- Просмотреть операционные документы и исторические изображения на личные
  сведения, которые владелец не хочет показывать публично. Автоматический
  поиск секретов не заменяет эту проверку.
- Сохранить локальную резервную копию Git и выбранных исходников, затем
  собрать накопленные изменения в логические коммиты. Не отправлять только
  прежний HEAD: в нём нет большей части текущих возможностей.

История Git не переписывается этим заданием. Игнорирование файла исключает
его из новой загрузки только если он ещё не отслеживался; ранее закоммиченные
данные могут оставаться в истории. Результат проверки истории — в отчёте.

## 5. Проверить будущий репозиторий из чистой копии

Проверить установку и выполнение проверок без локальных `.tools`, `.venv`
и `node_modules`. Чистые клиентские сборки и отдельная Python-среда проверены
в текущем аудите, но финальную копию нужно проверить после сборки коммитов.

Полный набор PostgreSQL-проверок достижений должен выполняться и в CI:
workflow теперь создаёт отдельную шаблонную тестовую базу и задаёт
`ACHIEVEMENT_TEST_DATABASE_URL`. Настоящие токены в GitHub Secrets для тестов
не нужны.

## 6. Закрытый репозиторий и первая отправка

Владелец прямо поручил первую загрузку в **Private**. Создан
[kasper-kasper/casper-loto](https://github.com/kasper-kasper/casper-loto),
закрытый доступ проверен через GitHub API. Владелец вошёл в GitHub и подтвердил
Git Credential Manager для локального Git и будущей работы через VS Code.

Проверить права подключённого GitHub на этот репозиторий. Для обычного `git push`
отдельно нужна авторизация Git на компьютере; доступ подключённого сервиса
не следует автоматически считать авторизацией локального Git.

Подключить remote, отправить согласованную ветку и проверить
[GitHub Actions](https://github.com/kasper-kasper/casper-loto/actions).
Открывать репозиторий всем без отдельного решения владельца не требуется.

## 7. Оформить страницу и проверить открытый вид

- Описание репозитория, ссылка на [Mini App](https://t.me/Kasper_loto_bot?startapp)
  и темы: `telegram-mini-app`, `python`, `fastapi`, `react`, `typescript`.
- Загрузить `github-social-preview.png` в Settings → General → Social preview.
- Проверить логотип, снимки, переключение README English / Русский и все ссылки
  уже на самом GitHub.
- Проверить Linux Actions, включая проверку символических ссылок, которая
  недоступна в текущей Windows-среде.
- Для заметного выпуска создать GitHub Release со ссылкой на Changelog.
  Каждую мелкую правку оформлять отдельным Release не обязательно.

После подключения обычные обновления отправляются через VS Code:
просмотр изменений → выбор файлов → Commit → Push.
