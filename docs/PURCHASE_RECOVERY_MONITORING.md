# Восстановление покупок и оперативный мониторинг

## Покупка при потере интернета

Mini App перед отправкой покупки сохраняет точный запрос и ключ `m1-…` в
localStorage. Журнал разделён по UUID аккаунта, полученному после авторизации
с сервера; токены и Telegram initData в него не записываются. Одновременно
разрешена одна незавершённая покупка. Если хранилище недоступно, запрос не
отправляется. Сетевой тайм-аут — 20 секунд; он не означает, что сервер отменил
покупку.

После перезагрузки, возвращения интернета или открытия приложения журнал
проверяется через авторизованный read-only endpoint purchase-receipts. Результат
восстанавливается из неизменяемого ledger, без новых списаний. Пока результат
неизвестен, интерфейс предлагает повторить **тот же запрос**, либо отменить
неподтверждённую попытку. Автоматическая проверка ничего не покупает.

Отмена использует transaction-level advisory lock, общий с покупкой. Если покупка
уже совершена, сервер возвращает её результат. Иначе создаётся уникальная
запись purchase_cancellations: любые поздние запросы с этим ключом отклоняются.
Эта запись — защита от запоздалого запроса, а не удаление билетов или возврат CAS.
Она сохраняется; финансовая история не изменяется. Старые клиенты и бот
сохраняют прежнее поведение ключей. Миграция — 0053_purchase_cancellations.

Обычная покупка привязана к первоначальному scheduled_at; повтор после смены
тиража не покупает автоматически билеты в следующий. Bingo уже привязан к draw_id.
Для корзины сохраняются идентификаторы купленных позиций: подтверждённые позиции
удаляются из хранилища до очистки журнала. Отметки использованных позиций
предотвращают их возвращение при сохранении старого состояния другой вкладкой;
они действуют в пределах срока жизни корзины / текущей браузерной сессии.

Восстановление работает на том же устройстве и в том же браузерном хранилище.
При очистке хранилища история билетов остаётся на сервере, но связь с конкретной
незавершённой попыткой на устройстве теряется.

## Мониторинг

Админка: **Система → Состояние → Скорость мини-аппа и контроль сервера**.
Авторизованный endpoint — GET /api/v1/admin/monitoring; публично метрики не доступны.

Сервер каждые 60 секунд проверяет просроченные тиражи, задержавшуюся доставку
обычных и распределительных постов, heartbeat планировщика, диск и завершённые
непустые резервные копии. Частичные dump-файлы не считаются успешными копиями.
Создание backup уже проверяет pg_restore --list; монитор проверяет наличие и
свежесть, а не выполняет ежеминутное восстановление всей БД. Backup подключён
к API только для чтения; финансовые таблицы монитор не изменяет.

Клиент отправляет ограниченные замеры первого готового экрана, загрузки главной
и покупки; сервер отдельно измеряет обработку запросов. Поля ограничены названием
метрики, длительностью и кодом ответа: комбинации, билеты, ключи покупки, имена,
initData и токены в метрики и diagnostic snapshots не попадают. Телеметрия не
блокирует интерфейс. Лимит — 20 клиентских замеров на аккаунт в минуту.

Окно скорости — последний час, максимум 10 000 замеров на показатель в памяти
одного API-процесса. После рестарта выборка начинается заново. JSON snapshot
пишется в обычный диагностический лог каждую минуту; действует существующая
ротация и архивирование. p50 — обычная скорость, p95 — верхняя граница для 95%
замеров; это наблюдения, а не гарантия скорости конкретного телефона.

Технические пороги предупреждений: диск занят ≥80%; резервной копии нет либо
она старше 26 часов; копий больше 7; тираж / доставка / heartbeat задержаны
на operational_stuck_minutes (по умолчанию 10 минут). Для скорости нужны хотя
бы 5 замеров: p95 открытия >4 с, покупки у игрока >2 с, покупки сервера >1 с.
Ошибка сервера или обрыв связи предупреждает при ≥10 замерах и доле ≥5%.
Ожидаемые отказы вроде нехватки CAS и закрытия продаж не считаются ошибками 5xx.

Независимый systemd timer k-loto-health-monitor.timer раз в минуту проверяет
четыре контейнера, публичный /health по HTTPS и наличие свежего snapshot API.
Это позволяет обнаружить остановку самого встроенного монитора. Его единственный
файл /opt/k-loto/.monitoring/state.json перезаписывается атомарно и подключается
к API read-only. История отдельных файлов не накапливается. Новые посты или
сообщения Telegram мониторинг не отправляет; существующие owner alerts о
зависших тиражах и уведомлениях продолжают работать.

Установка timer включена в release_vps.py для публикаций API под общим operations
lock. Для другого домена задайте K_LOTO_HEALTH_URL в systemd override. Диагностика:
systemctl status k-loto-health-monitor.timer и journalctl -u k-loto-health-monitor.service.
