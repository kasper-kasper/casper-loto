# Обычные достижения и профиль — локальная реализация

Дата: 19 октября 2026. Публикация на VPS владельцем явно исключена.

## Реализовано

- Ровно 22 утверждённых достижения категории `common`, с исходными ID и названиями.
  Каталог: [achievements.common.catalog.json](achievements.common.catalog.json).
- Кастомные игры по уточнению владельца: `september`, `pll`, `grob`
  («3 сентября», «2:22», Halloween). Grand — `weekly`, Ball — `pss`, классика — `khan`.
  FAST — `flash`, `shadow`, `pulse`; мгновенные — LIVE, Aurora, Vault.
- Покупка означает успешно оплаченный билет. Разные игры считаются по постоянным
  кодам, включая мгновенные. Возвраты уменьшают незавершённые счётчики; полученные
  достижения сохраняются, новых списаний и повторных наград нет.
- Выигрыши — окончательные выплаты по платному билету; сравнение с фактически
  уплаченной ценой (`payout_vs_price: eq/gt`). Bingo: один выигрышный билет,
  отдельный счётчик призовых составляющих. Старые билеты, в том числе рассчитанные
  после начала системы, исключены из этой партии.
- Ручной выбор сохраняется вместе с оплачиваемым билетом. Автоподбор, быстрые
  покупки, автоплей и выбор готовой Bingo-карточки не подменяют ручное заполнение.
  Неизвестное происхождение комбинации у старого клиента не считается ручным.
  Клиент передаёт происхождение выбора, а сервер подтверждает валидный билет,
  оплату и транзакцию; этот параметр сам по себе не выдаёт достижение или CAS.
- Для покупки одной операцией сохраняется неизменяемый UUID операции. Пять
  отдельных покупок не суммируются. Пять оплаченных билетов на пять тиражей
  в одной операции соответствуют условию. После выполнения этого разового
  условия повторных запросов подсчёта операции для него нет.
  События применяются в порядке подтверждённых операций: достигнутое в момент
  успешной оплаты сохраняется при последующем возврате независимо от скорости
  фонового обработчика. Итоговые незавершённые счётчики возврат уменьшает.
- Дни открытия считаются по Москве; повторный вход в тот же день идемпотентен.
  Клиент сообщает открытие/возвращение на передний план, а фоновые обновления
  не создают дни активности. Даты задаёт сервер.
- Выплата награды создаёт отдельное одноразовое событие. Собственная награда
  `first_achievement_reward` не запускает это же условие повторно.

## Интерфейс

- Баланс уменьшен с 207 до примерно 113 CSS px (около 46%); крупная картинка
  заменена компактной контурной иконкой. Имя игрока доступно отдельной строкой.
  Суммы в миллиардах показаны компактно, полная сумма остаётся в доступном описании.
- Под балансом — общий прогресс по всем опубликованным редкостям, три последних
  реально полученных достижения либо пустое состояние и переход в каталог.
- Отдельный экран: категории с реальными счётчиками, фильтры, сортировка на сервере,
  по 12 карточек с кнопкой следующей группы. Полученные идут первыми; незавершённые
  сортируются по доле выполнения, равные — по порядку каталога и ID.
  Одновременно показывается одна редкость; если между страницами изменился
  прогресс или версия каталога, первая группа обновляется без пропуска карточек.
- Подробности — нативное модальное окно с фокусом, закрытием и датой по Москве.
  Для разовых событий не показываются искусственные шкалы 0/1.
- Контурные SVG-иконки одного стиля. Цвет задаётся редкостью, а не конкретной
  карточкой. Сохранены пять редкостей основы, включая `uncommon`; секретность —
  независимый признак и дополнительный фильтр. Пустые категории скрыты.
- Уведомления показываются по очереди. Сервер хранит непросмотренные сообщения,
  клиент подтверждает показ. Запросы ограничены входом/возвращением и короткой
  серией после покупки; постоянного опроса достижений нет. Пропуск уведомления
  не влияет на получение достижения.

## Нагрузка

В запросах каталога и профиля не запускаются обработка игровых событий,
начисления или пересчёт билетов/выигрышей. Профиль запрашивает только три
последних достижения и сводные данные. Полный экран читает готовые показатели.
Обработчик проверяет условия, подписанные на изменившийся показатель.

Сохранены транзакционная очередь, ограниченные порции результатов, блокировки,
уникальные ключи и конечные каскады основы. Добавлены индекс UUID покупки и
частичный индекс непросмотренных уведомлений: выбираются максимум 10 сообщений
текущего игрока, затем снимки получений читаются по первичным UUID.

Объём аудитории и предел одновременной нагрузки VPS этой задачей не измерялись.

## Локальное использование

Подготовлена отдельная локальная БД `k_loto_achievement_common_20261019` на
`127.0.0.1:55439` в уже существующем локальном PostgreSQL. В ней импортированы
и включены ровно 22 определения, пользователей и получений — 0. Локальная
дата учёта — `2026-10-19T01:25:38.671013Z`; к официальному запуску production
она отношения не имеет. Проверочные пользователи жили только в удаляемых
тестовых копиях. Production не подключалась и не изменялась.

Только отдельная локальная БД с именем `k_loto_achievement_*`, с миграциями до
`0060_common_achievements`. Управляющая команда отвергает production и внешние БД.

```powershell
.venv/Scripts/python.exe -m alembic upgrade head
.venv/Scripts/python.exe scripts/achievements.py catalog docs/achievements/achievements.common.catalog.json
.venv/Scripts/python.exe scripts/achievements.py launch-local
.venv/Scripts/python.exe scripts/achievements.py drain --limit 100
.venv/Scripts/python.exe scripts/achievements.py status
```

Перед выполнением должен быть явно установлен `DATABASE_URL` отдельной локальной
БД. `launch-local` устанавливает единую дату начала один раз, без использования
предыдущей игровой истории. Для фоновой обработки в локальном API включаются
`SCHEDULER_ENABLED=true` и `ACHIEVEMENTS_WORKER_ENABLED=true`; Telegram-доставка
достижений остаётся выключенной. Обычные покупки не ждут выполнения очереди.

Для добавления/изменения поддерживаемого достижения достаточно JSON-каталога
и команды `catalog`. При изменении существующей записи увеличивается `version`.
Команда `common-catalog` импортирует исходную утверждённую партию как удобный
первоначальный вариант. Новые механики требуют соответствующего серверного
адаптера, а новые пороги уже поддержанных показателей — только конфигурации.

## До будущего запуска

Суммы наград **не назначены**. У всех 22 записей `reward_pending=true`, список
платёжных частей пуст. Получение сохраняется как `awaiting_config`; реальных
выплат нет. Интерфейс сообщает «Награда будет объявлена». Условие первой награды
реализовано и проверяется на синтетических выплатах, но без утверждённых выплат
обычный игрок пока не может его выполнить.

Владелец должен утвердить суммы и источник финансирования CAS (OD-066), а также
дату официального запуска. После этого нужен отдельный подготовленный выпуск,
включение обработчика и одноразовая активация на production. Локальные получения
и тестовые данные переносить в production нельзя. Изменение каталога не создаёт
платёжных частей для ранее полученных неоценённых достижений. Для их выплаты
потребуется отдельный согласованный сценарий.
