## Как добавить определение

Каталог — JSON-массив; синтаксическая схема:
[achievements.catalog.schema.json](achievements.catalog.schema.json).
Затем сервер проверяет поддержанность метрик, лотерей и адаптеров наград.
Описание полей и технических идентификаторов находится в ТЗ.

1. Подготовить запись с постоянным `code`, версией, редкостью, условием
   и списком частей награды; для неутверждённого черновика выключить
   `active` и `visible`.
2. Импортировать через управляющую команду. Изменённая запись требует
   повышения версии. Полученные снимки не перезаписываются.
3. Для нового фильтра результатов команда отдельно восстанавливает счётчик
   по уже обработанным после запуска фактам. Позиция незавершённого тиража
   предотвращает двойной учёт его следующей порции. Старый фильтр при повторном
   введении перестраивается заново, а не складывается со старым значением.
4. Для нового типа показателя зарегистрировать доверенный серверный адаптер.
   Он получает подтверждённое событие в транзакции и изменяет только проекцию.
   Клиент не может передавать себе прогресс или произвольные события.

Повторяемые достижения, произвольные скрипты условий и достижения, которые
должны появиться лишь от течения времени без события, в первую версию не входят.
Начальные прямые зависимости заменены счётчиками получений: каждый код
выдаётся один раз; CAS-каскад продолжается отдельным заданием.

## Локальные команды

Команды запуска и импорта намеренно запрещены в production и для удалённых БД.
Нужна отдельная loopback PostgreSQL с именем `k_loto_achievement_*`.
Не подставлять production DATABASE_URL.

```powershell
docker start k-loto-achievements-local
$env:APP_ENV = 'test'
$env:DATABASE_URL = 'postgresql+asyncpg://postgres@127.0.0.1:55439/k_loto_achievement_test'
.venv\Scripts\python.exe -m scripts.migrate_database
.venv\Scripts\python.exe -m scripts.achievements status
# Импорт владельческого JSON-каталога:
.venv\Scripts\python.exe -m scripts.achievements catalog 'путь-к-каталогу.json'
# Единственный запуск в этой локальной БД:
.venv\Scripts\python.exe -m scripts.achievements launch-local
.venv\Scripts\python.exe -m scripts.achievements drain --limit 100
```

Локальный runtime job включается `ACHIEVEMENTS_WORKER_ENABLED=true` только
при включённом общем scheduler. Для ручных тестов достаточно `drain`.
Отправка Telegram дополнительно требует `ACHIEVEMENTS_NOTIFICATIONS_ENABLED`,
согласия на бота и согласия на достижения; в этой работе её не включали.

`status` показывает очередь, ошибки и время самого старого задания.
После устранения причины остановки `retry <event_id>` разрешает новый цикл
попыток только незавершённого задания, сохраняя ключ дедупликации.

  Mini App **183 теста**, Admin **66 тестов**. Хеши исходников и сборок проверены.
- Проверены повторы, параллельные обработчики/награды, откат до фиксации

Реальная PostgreSQL проверяется через отдельную opt-in переменную
`ACHIEVEMENT_TEST_DATABASE_URL`. Тесты принимают только локальный шаблон
`k_loto_achievement_test`, клонируют для каждого сценария собственную БД
с UUID и удаляют только созданную ими копию. В обычном окружении эти тесты
пропускаются, а не подключаются к БД из `.env`.

Подтверждён нагрузочный сценарий 500 временных определений и 10 000 результатов:
один маркер тиража, 500 однократных получений, очередь полностью разобрана.

50 чтений баланса, p95 64,23 мс. Это SQL-чтение с подключением локального
стенда Windows/Docker, не задержка экрана и не показатель VPS.

Проверена настоящая покупка 1 000 билетов существующим сервисом. Три

На покупку сохраняются две записи очереди: сводка билетов и движение баланса.

## Ограничения и последующий запуск

- Система добавляет короткую транзакционную работу БД; нулевую стоимость
  обещать нельзя. Проверки и Telegram вынесены из ожидания пользователя.
- Прогресс обновляется в фоне. После большого тиража возможна очередь,
  её возраст и ошибки доступны диагностике. Настроек автоматического
  изменения игровой экономики нет.
- Новый фильтр восстанавливается управляющей операцией. Для крупной базы
  будущий production-регламент должен отдельно ограничить время такой
  переиндексации; текущая команда предназначена для локальной разработки.
- Квитанции обработки хранятся компактно, но не удаляются автоматически:
  они нужны для дедупликации и восстановления новых фильтров. Перед запуском
  определить мониторинг их размера и безопасную последующую компактизацию.
- У Telegram неопределённая доставка остаётся `UNCERTAIN`; сообщения
  автоматически не дублируются при потерянном подтверждении.

Перед production нужны утверждённые достижения, источник финансирования CAS,
финальные тексты/оформление, замеры на подходящем стенде, отдельный регламент
старта и явное разрешение владельца. Локальный CAS-адаптер проверяет прямое
ledgered начисление; источник настоящих наград не выбирался за владельца.
Расширять production compose/управляющие разрешения до этого не следует.
