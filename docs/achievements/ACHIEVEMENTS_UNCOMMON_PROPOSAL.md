## Техническая возможность пакетов, Grand и Bingo

В текущей первой версии адаптер подарка поддерживает один билет пяти ежедневных
лотерей, поэтому новая награда требует расширения, а не только правки числа.
Архитектуру перерабатывать не требуется. Предпочтительный вариант: разложить
пакет на 3–5 отдельных однократных частей существующей очереди; сохраняются
уникальная связь билета с частью награды, отдельные транзакции и возможность
довыпустить недостающие билеты после сбоя без повтора уже созданных.
В интерфейсе части группируются в «3 билета»/«5 билетов» одной лотереи.

Для Grand добавить разрешение недельного тиража, для Bingo — разрешение игры и
штатный выбор свободной карточки из пула. Обе игры уже используют общий сервис
покупки и расчёта. Лимиты, наличие мест, финансирование фондом и ожидание при
недоступности остаются обязательными. Выданные части сохраняются, остаток ждёт
ближайшего доступного тиража. Пакет — несколько билетов, а не игра на 3–5 тиражей.
Награды 22 обычных достижений остаются прежними: по одному билету там, где он есть.

## Проверенные механики и предлагаемые уточнения

- Bingo: механика уже существует. `domain/bingo.py` сохраняет ходы закрытия
  строк, первый тур имеет границу 18. Итог билета содержит `bingo_result.moves`.
  Для достижения достаточно хотя бы одной строки с ходом закрытия ≤18;
  закрытие дополнительных строк не мешает. Новые правила игры не нужны.
- «Дзынь!»: владелец подтвердил Casper Ball (`pss`) с призовой комбинацией 2+0.
  Лотерея не переименовывается. Для призовых сочетаний Ball/Dual необходима
  фактическая положительная выплата.
- «Сердечко ёкнуло»: предлагаем ровно 1 основное + 2 дополнительных числа,
  независимо от совпадения шифра; использовать версию правил снимка тиража,
  а не равенство одному внутреннему числовому коду результата.
- «Маленький Гранд»: предлагаем ровно 2 основных числа при любом числе
  совпавших дополнительных (2+0, 2+1, 2+2).
- «Дежавю»: предлагаем два соседних завершённых тиража одной лотереи, в каждом
  есть хотя бы один выигрышный платный билет игрока. Пропущенный игроком
  завершённый тираж разрывает серию, как и участие без выигрыша. Несколько
  выигрышных билетов одного тиража не образуют серию. Отменённый тираж не является
  завершённым. Мгновенные игры не образуют последовательность тиражей.
- «По чуть-чуть»: предлагаем дату официального тиража по Москве, для мгновенной
  игры — время успешного расчёта. Задержка фонового обработчика или восстановление
  пропущенных тиражей не сдвигают день. Требуются три разных ID лотерей и выплаты
  >0 по окончательно рассчитанным платным билетам. Мгновенные игры тоже считаются
  лотереями; если владелец хочет только тиражные, это надо утвердить отдельно.
- «Разносторонняя личность»: предлагаем три отдельные оплаченные игры за день:
  мгновенная, тиражная вне особой группы и особая (september/pll/grob).
  FAST относится к тиражным. Одна покупка особой лотереи не закрывает сразу
  две группы. День — дата успешной оплаты по Москве. Возвраты корректируют
  незавершённый прогресс без произвольного отзыва выданной награды.
- Количественные условия используют общие платные показатели с запуска системы,
  без обнуления при добавлении новой категории. 7 дней подряд — максимальная
  достигнутая серия реальных открытий; 14 дней — суммарно разные дни по Москве.
- Для совпадений не добавляется требование чистой прибыли: засчитывается
  утверждённый итог платного билета с нужной комбинацией. Bingo не размножает
  число выигрышных карточек по количеству призовых составляющих.

Все перечисленные трактовки утверждены владельцем вместе с наградами.

## Требования к реализации

Сохранить существующий движок и зелёную палитру uncommon. Добавить каталог из
23 записей, не меняя 22 common. Для накопительных условий использовать существующие
счётчики; для новых серий/дней — небольшие проекции по подтверждённым событиям.
Не сканировать историю при открытии приложения, не добавлять постоянный опрос
и не проверять весь каталог на каждое действие. Продумать однократную локальную
инициализацию новых проекций с исходной границы запуска; не запускать массовую
выдачу и не переписывать историю без отдельного решения владельца.

На этапе предложения тесты не запускались: исполняемый код не изменялся.
После утверждения выполнены сфокусированные тесты новых условий, дублей/конкуренции,
возвратов и границ московских дней, проверка совместимости общих счётчиков и
выдачи наград; frontend-проверки только затронутых компонентов и мобильный smoke.
Публикации на сервер не будет.
